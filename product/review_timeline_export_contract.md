# Review Timeline evidence export contract

## Status

This document approves a design contract for a possible future deterministic Review Timeline evidence export. The reserved format is `civil-estimate-review-timeline-export`, version 1.

**The export is not implemented.** There is no builder, verifier, browser route, download control, persistence layer, or accepted Timeline-export input in the current runtime. This contract does not authorize an implementation to weaken the existing Review Delta verifier or Review Timeline chain rules.

## Purpose and evidence authority

A future Timeline export may package one request-local, structurally verified Review Timeline as portable evidence. It is evidence chronology only. It is not a calendar history, estimate audit, source restoration, generated report, quality trend, readiness trend, approval record, or HeavyBid import artifact.

Creation must begin with the same **2–10 uploaded `civil-estimate-review-delta-export` v1 ZIPs** accepted by Review Timeline. In the export request itself, every Delta ZIP must independently pass `verify_review_delta_export()` and the complete set must pass the existing connected, acyclic, linear SHA-256 lineage contract. A prior browser result, hidden field, session value, filename, or claimed verified flag is not evidence authority.

The current Delta verifier intentionally returns bounded rows for browser preview. Those truncated preview rows are **not sufficient export evidence**. Before an exporter can be implemented, the strict verifier boundary must provide an internal canonical-evidence result only after all existing structural, integrity, and semantic checks succeed. The export must then contain every verified finding, governed-reference, and reference-metadata change row for every ordered transition, including `UNCHANGED` rows. It must never parse raw Delta members through an unverified side path or silently export only the browser preview.

Uploaded bytes and verified canonical evidence remain request-local. Creation writes no server-side file, creates no review session, and retains no uploaded or generated bytes after the response.

## Format identity and exact root members

The future ZIP identity is:

- export format: `civil-estimate-review-timeline-export`;
- export version: `1`;
- integrity format: `civil-estimate-review-timeline-export-integrity`;
- integrity version: `1`.

The exact root-file member set is:

- `manifest.json` — identity, ordered lineage/count summary, content declarations, and safety flags;
- `review_timeline.json` — canonical full verified Timeline evidence;
- `snapshots.csv` — one row for each ordered review-package snapshot;
- `transitions.csv` — one row for each ordered verified Delta transition;
- `finding_changes.csv` — every verified finding-change row from every transition;
- `reference_changes.csv` — every verified standard Activity/Resource reference-change row;
- `reference_metadata_changes.csv` — every verified standard reference-metadata-change row;
- `README.txt` — fixed human-readable scope and safety text; and
- `integrity.json` — SHA-256 and byte size for every other member.

All members are root files. Directories, alternate paths, duplicate names, missing members, and unexpected members are invalid. The Timeline export is neither a review-package nor a Review Delta export and must not be accepted by archived continuation, Review Delta comparison, Review Delta verification, or Review Timeline input routes.

## Canonical `review_timeline.json`

`review_timeline.json` is the sole canonical evidence member. It contains only:

- the supported export identity/version;
- an ordered `snapshots` array reconstructed from exact review-package SHA-256 continuity;
- an ordered `transitions` array corresponding one-to-one with adjacent snapshots; and
- the exact safety object defined below.

Each snapshot records its zero-based chain index, exact review-package SHA-256, supported package/integrity versions, source session mode, source filename, rows reviewed, and sorted unique descriptive package-filename aliases.

Each transition records its zero-based chain index, descriptive uploaded Delta filename, exact Delta-export ZIP SHA-256, exact Earlier/Later review-package SHA-256 values, recomputed finding/reference/reference-metadata counts, and the complete canonical verified change-row arrays from that Delta export. Delta filenames are labels only and never determine order, identity, or continuity.

No original Delta ZIP, review-package ZIP, estimate/reference file, packaged HTML, or other source bytes are embedded. Source filenames, review reasons, messages, recommendations, and reference labels remain archived evidence strings only; they are not instructions and are never rendered as active content by a future verifier.

## Deterministic ordering and serialization

The same accepted canonical evidence must produce byte-identical ZIP bytes.

- Snapshots and transitions use reconstructed SHA-256 chain order, never upload order, filenames, filesystem order, dates, or inferred chronology.
- Package-filename aliases are unique and sorted by Unicode code point.
- Finding rows are sorted by `(sheet, row, rule_id, field)` within each transition.
- Reference rows are sorted by `(reference_type, sheet, source_row, code)` within each transition.
- Reference-metadata rows are sorted by `role` within each transition.
- Changed-field name lists are unique and sorted by Unicode code point.
- JSON uses UTF-8, `ensure_ascii=false`, two-space indentation, lexicographically sorted object keys, and one trailing LF.
- Embedded JSON cells in CSV use compact UTF-8 JSON with lexicographically sorted object keys.
- CSVs use the exact headers below, chain/row order above, a header even when there are no evidence rows, and CRLF record endings. A cell whose left-trimmed text begins with `=`, `+`, `-`, or `@` is prefixed with a single apostrophe.
- ZIP members are written in lexicographic member-name order with DEFLATE compression. The ZIP header date is fixed to `1980-01-01 00:00:00` as non-semantic format metadata; no member contains a timestamp/date field and no time value is inferred from it.

Exact CSV headers:

- `snapshots.csv`: `snapshot_index,package_sha256,package_format,package_version,integrity_version,source_session_mode,source_filename,rows_reviewed,package_filename_aliases_json`
- `transitions.csv`: `transition_index,delta_filename,delta_export_sha256,earlier_package_sha256,later_package_sha256,finding_counts_json,reference_counts_json,reference_metadata_counts_json`
- `finding_changes.csv`: `transition_index,delta_export_sha256,change_type,sheet,row,rule_id,field,evidence_fields_changed_json,review_fields_changed_json,before_json,after_json,before_review_json,after_review_json`
- `reference_changes.csv`: `transition_index,delta_export_sha256,change_type,reference_type,sheet,source_row,code,fields_changed_json,before_json,after_json`
- `reference_metadata_changes.csv`: `transition_index,delta_export_sha256,change_type,role,fields_changed_json,before_json,after_json`

## Manifest and integrity

`manifest.json` is deterministically regenerated from `review_timeline.json`. It repeats no full evidence rows. It records:

- export and canonical-evidence identity/version;
- ordered snapshot and transition counts;
- first/last review-package SHA-256 and the ordered transition lineage;
- per-transition recomputed finding/reference/reference-metadata counts;
- exact member declarations;
- `original_delta_exports_included=false`;
- `original_review_packages_included=false`;
- `original_estimate_reference_bytes_included=false`;
- `operational_session_evidence_included=false`; and
- the exact safety object.

`integrity.json` identifies the supported export/integrity formats and versions. Its sorted `members` map contains exact `size_bytes` and lowercase SHA-256 for every member except `integrity.json` itself.

The fixed `README.txt` must say that the bundle preserves verified archived evidence chronology only, cannot prove source currency/correctness/improvement/approval/readiness/reference authority/HeavyBid validity, contains no original input bytes or Operational Crew/Production evidence, and contains no generated narrative or score.

## Exact safety object

Creation and verification must require these exact boolean values and reject missing, extra, non-boolean, or relaxed fields:

- `evidence_chronology_only=true`;
- `session_created=false`;
- `persistence_created=false`;
- `source_restoration_performed=false`;
- `re_audit_performed=false`;
- `reference_rerun_performed=false`;
- `calendar_chronology_inferred=false`;
- `source_currency_inferred=false`;
- `generated_narrative_included=false`;
- `quality_trend_inferred=false`;
- `improvement_regression_inferred=false`;
- `readiness_inferred=false`;
- `operational_evidence_reconstructed=false`;
- `heavybid_writer_performed=false`; and
- `heavybid_import_validated=false`.

The export must not add a timestamp, date, duration, revision rank, trend direction, better/worse label, score, recommendation, or generated narrative outside the already verified archived evidence strings.

## Bounds and fail-closed creation

The input boundary remains 2–10 Delta ZIPs, at most 50 MB compressed per Delta, and at most 502 MB for the aggregate multipart request including form overhead. The future Timeline export is bounded to 502 MB compressed, 250 MB per uncompressed member, and 750 MB total uncompressed content. These bounds do not relax any existing per-Delta member or uncompressed limits.

Creation must fail before returning export bytes when:

- any input fails independent Delta verification;
- canonical full evidence is unavailable from the strict verified path;
- the set fails any existing Timeline lineage/identity/count/chain rule;
- counts do not exactly recompute from full verified rows;
- anchors or metadata roles violate the Delta contract;
- ordering/serialization cannot be canonicalized;
- any exact safety value or excluded-content declaration differs;
- any input or output bound is exceeded; or
- any requested option would add timestamps, narratives, scoring, persistence, source restoration, rerun behavior, Operational Crew/Production evidence, or HeavyBid behavior.

There is no partial, preview-only, best-effort, or unverified export mode.

## Future independent verification contract

Implementation of creation does not authorize distribution until an independent in-memory verifier is implemented in the same or an earlier guarded increment. The verifier must:

1. enforce the exact root member set and compressed/member/total-uncompressed limits before semantic use;
2. reject unsafe paths, directories, duplicates, encryption, unreadable ZIP content, and unsupported format versions;
3. verify the complete `integrity.json` member map, byte sizes, and SHA-256 values;
4. validate the canonical JSON types, exact safety object, supported snapshot/transition identities, full row vocabularies, unique anchors/roles, adjacency, counts, and one connected acyclic linear chain;
5. deterministically regenerate and byte-compare the manifest, five CSVs, and fixed README from `review_timeline.json`; and
6. return bounded escaped preview evidence only, create no session, write nothing to disk, and perform no source restoration, re-audit, reference rerun, narrative generation, scoring, or HeavyBid action.

Successful verification proves only the Timeline ZIP's structure, hashes, deterministic regeneration, and internal semantic consistency. Because original Delta/review-package/source bytes are excluded, it does not re-verify those absent inputs, authenticate lineage externally, establish calendar chronology or source currency, or prove estimate correctness, improvement/regression, approval, reference authority, bid readiness, or HeavyBid import validity.

## Operational and HeavyBid boundary

Operational Crew Code / Production Rate evidence remains session-only and outside review-package v1 and Delta-export v1. This contract does not make it portable and does not reconstruct, summarize, infer, or invent Bid Item, Activity, Resource, Crew, Production, Rate, or Quantity values.

No Timeline export can be a controlled-output eligibility decision, HeavyBid candidate file, writer input, import action, or import validation record. `HEAVYBID_IMPORT_VALIDATED=false` remains immutable under this contract.

## Explicit non-goals

- no exporter, verifier, route, UI control, or accepted input in this contract-only increment;
- no timestamps or inferred dates;
- no generated narratives or trend/quality/readiness scoring;
- no persistence or cross-request/cross-route transfer of evidence or verification state;
- no source restoration, source-currentness claim, re-audit, or reference rerun;
- no Operational Crew/Production reconstruction or portability;
- no HeavyBid writer/import claim or action; and
- no invented estimating values.
